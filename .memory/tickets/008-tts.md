# 008 — Text-to-speech via Piper

**Status:** implemented (Piper). Edge/Kokoro deferred.
**Created:** 2026-11-06

## Goal

Let a composition contain narration without shipping any audio files: the text
lives in the script, speech is synthesised locally at render time.

```ts
s.say("नमस्ते, यह Kino से बनाया गया है।", { voice: "hi_IN-rohan" })
s.audio([{ src: tts("Kino is scripting-first.", { voice: "en_US-lessac-medium" }) }])
```

## Why Piper

Measured, not guessed (VoxRT CPU benchmark, Nov 2026; and reproduced here):

| Model | Weights | Speed (1 core) | Hindi | Licence |
| --- | --- | --- | --- | --- |
| **Piper medium** | **~63 MB** | **6% RTF (17x real time)** | **yes** | engine GPL-3.0 |
| Kokoro-82M | 326 MB + 28 MB voices | 52% RTF, 1.2 GB RSS | **no** | Apache 2.0 |
| Supertonic 3 | ~99M | CPU | yes | OpenRAIL-M, **archived Jul 2026** |

Piper is the only option that is simultaneously tiny, fast on one core, and
Hindi-capable. Kokoro is the better English voice but has no Hindi and is an
order of magnitude heavier. Supertonic is dead upstream.

## Licensing boundary (important)

Piper's **engine is GPL-3.0**. Kino therefore **spawns the `piper` binary and
never imports, bundles or links it** — the same subprocess boundary used for
ffmpeg and yt-dlp. `src/tts/piper.ts` contains no Piper code, only an
invocation. Do not add `piper-tts` as a dependency.

## Design

- **Provider:** `src/tts/piper.ts` — `tts()`, `synthesizeToWav()`,
  `ensureVoice()`, voice catalogue, cache keys.
- **Resolution:** `src/tts/resolve.ts` — `render()` awaits `resolveTtsTracks()`
  before `compile()`, because compile is synchronous. `compile()` therefore
  only ever sees real WAV paths.
- **Scene narration:** `s.say()` attaches specs to `scene.narration`;
  normalization lifts them into composition audio at the scene's start time,
  which is where transition overlap is already accounted for.
- **Guard:** if a `TtsSpec` ever reaches `normalizeAudio()` unresolved, it
  throws instead of handing FFmpeg an object.

## Measuring narration (2026-11-07)

`tts()` defers synthesis, so it cannot answer "how long is this line?".
`await voice(text, opts)` synthesises now (cache-first) and returns
`{ seconds, path, spec, ... }`; `wavDuration()` parses the WAV `fmt `/`data`
chunks via `byteRate`, so it is correct for any sample format and clamps a
truncated file to the bytes actually present.

`duration: { fit: voice, pad?, lead?, min? }` sizes a scene to
`lead + seconds + pad` (pad default `NARRATION_PAD = 0.6`). Fits are resolved
in `normalizeCompositionFull()` **before `validateComposition()`** — the
validator rejects an object, and everything downstream (offsets, transition
overlap, element defaults) must see a number. `s.say(voice)` pushes
`voice.spec`, so the measured audio is reused rather than synthesised again.

Gotcha: `voice()` spawns Piper (~7s cold, ~1ms on a cache hit). Measure lines
in parallel and keep the result in a variable; do not call it inside a scene
callback, which runs synchronously.

## Captions (2026-11-07)

`src/captions/` turns a measured line into timed elements. No speech
recognition: the words are already known from `s.say()`.

- **Even timing** (`evenTimings`) — words weighted by length, silence after
  punctuation, pause budget capped at 30% of the line. Accurate enough for TTS.
- **Aligned timing** — `mms-forced-align` (MIT, onnxruntime-node, ~317 MB
  model). Loaded lazily; a *missing package* falls back to even timing, but a
  failure inside the aligner is surfaced rather than hidden. One aligner per
  process. Measured on a real line: scores 0.94–1.00 and per-word corrections
  up to 220 ms versus even timing.
- **Where it lives** — `kino setup captions` runs `npm install --prefix
  ~/.cache/kino/captions`, *not* the project: no manifest, no lockfile, one
  copy shared by every project. A project-local install still wins if present.
  `loadAligner()` falls back to the cached copy by absolute path.
- **Decoding** — alignment needs 16 kHz mono float PCM, produced by Kino's own
  resolved ffmpeg binary (`getFFmpegBinaryPath`), not a second ffmpeg on PATH.
- **Styles** — `karaoke` (default), `word`, `block`.

Rendering the highlight: drawtext colours an entire string, and its
`fontcolor_expr` is evaluated once per text, not per glyph. So a karaoke sweep
is a second copy of the line in the highlight colour, cropped to the active
word's box and overlaid. Consequences worth remembering:

- `crop`/`overlay` have no `text_w`/`text_h` and their `w`/`h` are the *input*
  size, so the highlight copy is emitted with `main_w`/`main_h` and all word
  boxes are computed as plain pixel numbers at compile time.
- Word boxes use the normalizer's own `wrapText`/`estimateTextWidth`, so the
  crop agrees with the wrapping drawtext actually performs. Estimating from the
  unwrapped line put the highlight on the wrong line for wrapped captions.
- `formatTextBasePosition` emits nested forms like `((h-text_h)/2)+(240)`;
  resolving those needed a small recursive evaluator, not a regex. A regex
  silently produced `y=0` and `y=-8`, which looked like "no highlight".

## Deferred

- **Hinglish/Devanagari alignment.** The aligner's vocabulary is `a–z` +
  apostrophe; Indic scripts need its romanization path, not wired up here.
- **Word-by-word reveal** (words appearing one at a time rather than lighting
  up) — currently the whole caption line is visible from its start.

## Caching

| What | Where | Key |
| --- | --- | --- |
| Voices | `~/.cache/kino/tts/voices` | voice id |
| Audio | `~/.cache/kino/tts/audio` | `sha256(piper:voice:rate:text)` |

Both are **global**, not per-project: the same line in the same voice is the
same WAV, so a second project reuses the first one's audio. Voice downloads are
temp-then-rename, so an interrupted fetch never leaves a truncated model.

## Pitfalls found while implementing

- **Voice URL layout.** The directory drops the quality suffix
  (`.../lessac/medium/`) but the file name carries it exactly once
  (`en_US-lessac-medium.onnx`). Ids that already end in the quality
  (`hi_IN-rohan`) must not get it appended again. Both bugs shipped into a
  first draft and were only caught by a real render — now covered by a URL test.
- **`piper` writes a benign onnxruntime PCI-bus warning to stderr.** Do not
  treat stderr as failure; check the exit code and the output file.
- **`--length-scale` is the inverse of rate.** Faster speech is a shorter
  scale, so `rate: 2` passes `--length-scale 0.5`.
- **`--dry-run` must not download.** A voice fetch is ~63 MB and piper is a
  subprocess; dry runs skip both. `replaceTtsWithPlaceholders()` swaps specs for
  `tts-pending.wav` so the printed command is still inspectable. Verified by
  running the dry run with `piper` absent from `PATH`.
- **Do not import `cli.js` from tests.** It executes the CLI on import. The
  dry-run helper lives in `tts/resolve.ts` for that reason.

## Deferred

- **edge-tts.** The unofficial Bing Read Aloud endpoint. v1 `Sec-MS-GEC` tokens
  were killed in **October 2026**; the current v2 token is
  `<16 hex CS64>-<64 hex SHA256>`, and `Sec-MS-GEC-Version` must be
  `2-<chromium>`. Reimplementing CS64 in TypeScript is fragile and Microsoft
  has now broken this twice. If added, shell out to the `edge-tts` CLI when it
  is on PATH rather than porting the protocol.
- **Kokoro.** Best-in-class English at 82M, but no Hindi and ~10x Piper's
  footprint. Worth adding as an opt-in English provider later.
- **Hinglish in one voice.** Piper switches voices at a language boundary, so a
  code-mixed sentence sounds like two speakers. Veena (Apache 2.0, 3B, native
  code-mixing) is the answer if that matters — GPU-only.
